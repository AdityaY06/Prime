## Design decisions (documented in-code)
- **PERCENT, not absolute ms, for the score** (Plews 2013 idiom): `hrvPctDeviation = (today − baseline)/baseline × 100`, signed, 1 dp. Absolute ms ride alongside for display ("HRV 42MS −15%" driver label; "7-DAY BASELINE 50 MS · −16% VS BASELINE" card line).
- `hrvContribution`: ≥+5% → +5 · −8%..+5% → 0 (normal day-to-day RMSSD variation) · ≤−8% → −5 · ≤−20% → −10. Boundaries inclusive at −8/−20/+5. Softer than RHR's +10/−15 (HRV is noisier — informs, doesn't dominate). Exported `HRV_PCT_THRESHOLDS` = single source; coach.ts mirrors via `COACH_THRESHOLDS.hrv*Pct`.
- `baselineFromRows` shared private core (mean + prior-day count); `rhrBaselineFromRows` public signature + semantics byte-identical (verified against an inlined pre-change reference across 30+ fixtures); `hrvBaselineFromRows` = same contract.
- `HrvTrendView` diverges from `RhrTrendView` in ONE honest way: baseline/pctDeviation nullable while forming, + `baselineDays` numerator → "BASELINE FORMING — N/3 DAYS" instead of silence. Null only when no recent (≤2-day) value. Non-positive baseline (defensive-pure) → null pct, no div-by-zero.
- **Coach no-double-count**: HRV suppression is INSIDE readinessScore now (−10 at ≤−20% → band drags to MODERATE/BACK OFF → existing RECOVERY/REST branches fire). The new rule-3 HRV branch fires ONLY when `readinessBand === null` — unreachable via the real API (hrvPctDeviation implies a readiness component implies a band), a defensively-pure guard documented with the full reasoning at the branch. HRV evidence ROW always renders (evidence, not a second verdict switch).
